# 🐒 MechApe — Roadmap

The guiding rule for everything here: **local by default, honest always.** Nothing on this list may ever *require* an account, a cloud service, or sending your data off the machine — anything remote (like the optional OpenRouter backend) is opt-in, per chat, and clearly labeled. Ideas are grouped by the promise they serve — keeping MechApe **local-first, honest, and yours**.

Have an idea? Open an issue — local-first, private-by-default proposals move to the top.

## Next up

The current focus, in priority order (details in the sections below). The backend is now fully self-owned after the Ollama removal, and the GPU-selection gaps that migration left behind are closed — so this round returns to the daily-tool work, with one piece of unfinished verification at the top:

1. **Work out why Vulkan is slower than CPU on NVIDIA** — measured on the dev laptop (RTX 3070 Laptop, llama3.2 3B Q4): CPU-only **15.3 tok/s** generation vs Vulkan full-offload **1.9 tok/s**, with an identical Vulkan run minutes earlier hitting 16.9 tok/s. Fast prompt eval alongside collapsed generation points at weights not staying resident in VRAM. **The default has been switched to CUDA on NVIDIA in response** (2026-08-07), but that is a workaround for a symptom nobody has explained — the underlying Vulkan behaviour still wants diagnosing, since Vulkan remains the bundled default for AMD and Intel and may be underperforming there too. Needs repeat runs, a VRAM watch, and a CUDA-vs-Vulkan comparison on the same model rather than the single noisy sample behind this note
2. **Finish real-hardware verification** — the backend now has a real first run behind it, which immediately found three things unit tests could not: the extractor froze the app, the CUDA build silently reported no GPU (its runtime ships separately), and Vulkan enumerates the integrated GPU ahead of the discrete one. All fixed and re-verified against the real binaries. **Still unproven: an actual model generating tokens** — the device pin, the GPU→CPU load fallback, and end-to-end chat have not run against real weights yet
3. **Verify macOS & Linux** — the binary-resolution and platform logic was written for all three platforms but has only had a hands-on pass on Windows; needs to actually be run and fixed up on the other two before calling them supported
4. ~~**Search across chats & projects**~~ — **shipped**: ⌕ Search in the rail (or Ctrl+K) searches project names, chat titles, and every message at once, with match-centered snippets and jump-to-exact-message
5. **Edit · regenerate · branch messages** — fix a prompt and re-run, branch an alternate take, copy a conversation as Markdown *(shipped so far: ↻ retry on the last reply; edit-and-resend on any past message of your own, with a heads-up before discarding more than its own reply; copy/save a whole conversation as Markdown, real source not a flattened render. Remaining: branching an alternate take without losing the original)*
6. ~~**Backup & wipe controls**~~ — **shipped**: Preferences → Data & backup — one-click backup (zips the data dir to a folder you pick) and a real "erase everything" (projects, chats, and cached embeddings) gated behind typing the exact confirmation phrase, plus a live project-count/data-path readout and an "Open data folder" shortcut in the desktop app
7. **Theming** — palette presets, light/dark/system, font & density controls (the UI already runs on CSS variables) *(shipped so far: seven presets in Preferences → Theme — dark: Cyber Deco, Speakeasy Noir, Gothic Library, Midnight; light: Parchment, Daylight, Porcelain — applied pre-paint, persisted, all WCAG-AA contrast-checked. Remaining: system-follow toggle, custom colors, fonts, density)*
8. **Completion notifications** — a desktop toast (optional sound) when a long generation finishes while MechApe is in the background

*(The CA-signed certificate is deliberately deferred for now.)*

### OpenRouter deepening

Folding in the parts of OpenRouter's API that serve MechApe's promises — privacy first, then cost transparency, then writing workflow:

- [x] **Privacy routing by default** — remote requests demand `data_collection: deny` (only providers that don't log/train see your words), with a Preferences opt-out for wider provider choice
- [x] **Cost per reply** — token counts and exact $ cost under each remote reply, plus a running per-chat total in the header (the remote sibling of the local token meter)
- [x] **Credits & key check in Preferences** — a live "$ used (of $ limit)" readout next to where the key is saved
- [x] **Reasoning-model support** — R1-class models stream their thinking separately; it renders as a collapsible "thinking…" block (open while the model thinks, folded once the answer starts) and persists with the message
- [x] **Free tier & routing variants** — a "free only" filter in the browse dialog, and a per-project `or_route` option (`floor` = cheapest provider, `nitro` = fastest)
- [x] **Prompt caching** — automatic cache markers on the system prompt for models that support it (Claude, Gemini); big savings for the resend-the-manuscript editing pattern
- [ ] **Fallback models** — an ordered backup list so a provider outage fails over instead of erroring
- [ ] **Web search per chat** — OpenRouter's search plugin, opt-in and badged like remote itself (it's a second place your query text goes)

- [x] **Own the whole local stack** (2026-08-06) — replaced the Ollama dependency entirely: MechApe now downloads and SHA256-verifies its own `llama-server` binary (Windows CUDA-with-CPU-fallback; macOS/Linux written but untested), runs two loopback-only instances (chat + embed) it spawns and respawns itself as you switch models, and models are plain `.gguf` files pulled straight from a Hugging Face repo — no registry, no separate install, nothing to start yourself in the desktop app. Supersedes the "Self-contained Ollama" item that used to be here; killed cleanly on quit instead of left running, since it's no longer a shared system daemon
- [x] **CUDA is the default on NVIDIA again** (2026-08-07) — the build is now chosen by what hardware is actually present, not by download size. MechApe probes the bundled Vulkan build (it enumerates every vendor's GPU, costs under a second, and is already on disk) and takes **CUDA → Vulkan → CPU** where an NVIDIA card turns up, **Vulkan → CPU** otherwise. This reverses the earlier Vulkan-first default, which had been chosen to keep the first run download-free and turned out to cost roughly 8x generation throughput on NVIDIA. AMD and Intel are never offered CUDA, since it cannot see their cards. The Preferences control flipped from opt-in to opt-out accordingly, and the honest cost is stated there: choosing CUDA means a one-time ~640 MB download, which is the one remaining place the fetch-then-execute pattern still applies
- [x] **The runtime ships in the installer** (2026-08-07) — `npm run dist` now fetches, SHA256-verifies and unpacks the Vulkan and CPU builds at *build* time (`scripts/fetch-runtime.js`) and electron-builder packages them, so there is no first-run download and nothing is fetched-then-executed at runtime. That pattern is what antivirus engines target, and this project proved it the hard way: Avast quarantined `llama-server.exe` from both build folders (leaving the other 21 executables untouched — it wants the binary that opens a listening socket), then took Electron itself, breaking the dev setup entirely. The bundle is also trimmed to just the server and its shared libraries: 21 unused CLI tools and their private `-impl` DLLs are dropped per variant, which is mostly about putting 42 fewer unsigned executables on a user's disk rather than the 11 MB it saves. Only the opt-in CUDA build still downloads, at ~640 MB
- [x] **Survived its own first real launch** (2026-08-06) — the first genuine run on real hardware froze on the splash, and the post-mortem found three separate problems no amount of unit testing would have caught. (1) Extraction used `adm-zip`, which reads the whole archive into memory and materializes each entry as a Buffer — fine for a few KB of skill markdown, fatal for a 250 MB archive holding a 537 MB DLL, and it ran on Electron's main thread. Now streamed through `bsdtar` in a child process: **2.9 s instead of a hang**, flat memory. (2) `tar` had to be resolved explicitly to `System32\tar.exe`, because Git for Windows puts *GNU* tar on PATH, which refuses zip and misreads `C:\...` as a remote host. (3) The CUDA build reported **no GPU on a working RTX 3070** — llama.cpp packages the CUDA runtime as a separate 391 MB archive, so `ggml-cuda.dll` never loaded. Also added: first-run progress on the splash (a silent multi-minute download is indistinguishable from a hang), reuse of an already-verified download instead of re-fetching, and a completeness check so a half-installed build is never reused
- [x] **Picks the right GPU build, the right GPU, and survives a model that won't fit** (2026-08-06) — Windows now walks **Vulkan → CPU** (CUDA opt-in in Preferences), asking each build what devices it can actually see (`--list-devices`, which really initializes the backend) instead of the old `--help` check that only proved the binary starts. That brings **AMD and Intel GPUs** in via Vulkan, and catches "CUDA build, no NVIDIA card" at boot rather than as a crash at first chat. Underneath it, a model that fails to load on the GPU (usually weights + KV cache over VRAM) now retries once on CPU instead of failing the chat — session-only, so a restart gives the GPU another chance. Builds download lazily (one archive in the common case), the probe fails *open* so unparseable output never demotes a working GPU machine, and the status pill names what's actually running (**local models · CUDA / · Vulkan / · CPU**) so a fallback is visible instead of just slow. **Verified against unit tests and a stubbed backend only — not yet run on real GPU hardware**
- [x] **Hardened & correctness-audited the local backend** (2026-08-06) — an independent security review plus a 4-angle cleanup pass (reuse, simplification, efficiency, altitude) on the new backend found and fixed: an NTFS alternate-data-stream gap in model-name validation, a PID-reuse edge case that could — in a rare window — kill an unrelated process on quit, a concurrent model-switch race that could fail an unrelated request with someone else's error, a 64 MB *synchronous* disk read on every Model Info click that could stall an in-progress chat stream, and Zip-Slip protection on the downloaded binary's extraction (defense-in-depth — the archive is already SHA256-verified). Also deduped two independently-drifting "stream a download to disk" implementations into one shared, tested module. 31 tests now cover the backend end to end

## More secure

*The base is already strong — loopback-only, Host/Origin checks, CSP, a sandboxed renderer, path confinement. These push from "safe by design" to "safe by default, and defensible to hand to someone else."*

- [ ] **Encryption at rest** — chats, projects, and the retrieval indexes (which hold chunked attachment text) are plaintext JSON (great for inspection, less so on an unencrypted disk). Add an optional encrypted data folder, or surface a clear "enable device encryption" note in Preferences
- [~] **CA-signed certificate** — the release pipeline is built and waiting on paperwork. `.github/workflows/release.yml` builds on a version tag and signs through SignPath Foundation (free for open source) in two passes: every binary inside the unpacked app, then the installer built from those signed files. Signing the app's *contents* is the part that matters here — the file scanners quarantine is `llama-server.exe` sitting on disk after install, not the installer. SignPath fetches the artifact from the workflow run and verifies its origin, so this can only ever work from CI, never a local build. Remaining: submit the application at signpath.org/apply (manual review, expect weeks), then set one secret and three variables. Full setup in [docs/SIGNING.md](docs/SIGNING.md). Until then the workflow publishes unsigned and says so in the release notes, so releases aren't blocked on the approval
- [ ] **Auto-update** for the desktop app (`electron-updater`) — with pinned signature verification when it lands
