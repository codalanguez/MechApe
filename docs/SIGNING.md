# Code signing

MechApe's Windows releases are signed by [SignPath Foundation][foundation],
which provides free code-signing certificates to open-source projects.

## What signing fixes, and what it doesn't

MechApe ships `llama-server.exe` and its GPU backend libraries inside the
installer. That binary is small, unsigned upstream, and opens a listening
socket — behaviourally indistinguishable from a malware dropper, which is
what heuristic scanners are built to notice.

This is not hypothetical. During development Avast quarantined
`llama-server.exe`, then Electron itself, then the app's own executable,
while leaving the other twenty-one executables in the same folder alone.
Adding an exclusion did not clear it: the block was cached in the running
service rather than the chest.

Two changes address that, and it is worth being precise about which does
what:

1. **Bundling the runtime in the installer** (`scripts/fetch-runtime.js`)
   removes the download-then-execute pattern entirely. Done.
2. **Signing** removes the SmartScreen "unknown publisher" warning from the
   installer and from `MechApe.exe`, and gives both an identity that
   reputation systems can accumulate trust against.

**Signing does not fix the `llama-server.exe` quarantine.** The SignPath
Foundation code of conduct permits a project to sign only artifacts built
from its own source, and requires upstream OSS binaries to ship *unsigned*
inside the signed package. `llama-server.exe` comes verbatim from
[ggml-org/llama.cpp][llamacpp] — it is exactly the file we are not allowed
to sign. It stays unsigned on disk after install and remains exposed to
behaviour-shield heuristics.

The policy points at the real remedy: ask upstream to sign their own
releases, and point them at SignPath Foundation if they want the same free
certificate. That is worth an issue on the llama.cpp tracker, and it is not
in this project's control.

## What actually gets signed

Almost nothing in the package is ours in the sense the policy means:

| Component | Origin | Signed |
| --- | --- | --- |
| `MechApe.exe` | our build's Electron host | **yes** |
| `MechApe Setup <version>.exe` | produced by our build | **yes** |
| `resources/runtime/**` — llama-server, ggml, mtmd | ggml-org/llama.cpp, verbatim | no — upstream |
| `ffmpeg.dll`, `libGLESv2.dll`, `vk_swiftshader.dll`, … | Chromium / Electron | no — upstream |
| `resources/app/**` | ours, but it is JavaScript | nothing to sign |
| `Uninstall MechApe.exe` | generated by NSIS inside the installer | no |

`.github/workflows/release.yml` therefore signs two named files rather than
globbing the tree. An earlier revision of that workflow submitted the whole
unpacked directory with a `**/*.exe;**/*.dll` filter, which would have
signed the entire llama.cpp runtime — a policy violation that would have
been caught at review, or worse, after.

## Eligibility

The Foundation's [conditions for open-source projects][conditions], against
MechApe:

| Condition | Status |
| --- | --- |
| No malware or unwanted programs | ✅ |
| OSI-approved license, no commercial dual-licensing | ✅ MIT |
| No proprietary components | ✅ |
| Actively maintained | ✅ |
| **Already released in the form to be signed** | ❌ **no tagged release yet** |
| Functionality documented on the download page | ✅ README + project page |
| Code signing policy on the project home page | ✅ see README |
| MFA on GitHub and SignPath for all team members | ⚠️ verify before applying |
| Verifiable reputation | ⚠️ the weak point — see below |

Two of those need action before applying.

**Released** is a hard blocker: there must be a published release before
they will consider the application. Tag a version and let the workflow
publish it unsigned.

**Reputation** is the one that decides it. The Foundation is explicit that
executable programs — as opposed to developer libraries — need "a certain
verifiable reputation," because their name is on the certificate. A new
repository with no downloads is a weak application no matter how good the
code is. There is a genuine chicken-and-egg problem here (an unsigned build
that triggers SmartScreen and antivirus is exactly what stops a project
accumulating users), and it is fair to say so plainly in the application
rather than dress up the numbers.

## Team roles

The policy requires named roles even for a single maintainer:

- **Authors** — may commit without additional review.
- **Reviewers** — must review any change proposed by a non-committer.
- **Approvers** — approve each individual signing request.

For a solo project one person holds all three. The reviewer obligation still
binds: outside pull requests get reviewed before merge.

## Applying

Apply at <https://signpath.org/apply>. Review is manual; plan on weeks.

The origin verification is the part worth understanding: SignPath does not
accept an uploaded file. It reaches into the workflow run through the GitHub
API and pulls the artifact itself, then checks the run came from the
registered repository, branch and workflow. That is why the build must
happen in CI, and why a locally built installer can never carry this
certificate — by design. It also means build scripts and CI configuration
are part of the trusted surface, and deserve the same review attention as
application code.

## Configuring the SignPath project

Once approved:

1. Create a project; its **slug** is `SIGNPATH_PROJECT_SLUG`.
2. Add a **trusted build system** for GitHub Actions and link the repository.
3. Create two **artifact configurations**, named as the workflow expects:
   - `application` — a single PE file (`MechApe.exe`)
   - `installer` — a single PE file (the NSIS setup)
4. Create a **signing policy** (e.g. `release-signing`) and grant the GitHub
   Actions build system permission to submit against it. Its slug is
   `SIGNPATH_SIGNING_POLICY_SLUG`.
5. Generate an **API token** for CI submission.

Both configurations must carry **metadata restrictions**, which the policy
requires: product name pinned to the project name, and product version
identical across every file in a build. MechApe's build already produces
consistent values (`MechApe` / the `package.json` version), so this is a
matter of declaring them so SignPath enforces it. Roughly:

```xml
<artifact-configuration xmlns="http://signpath.io/artifact-configuration/v1">
  <pe-file>
    <authenticode-sign>
      <metadata-restrictions>
        <product-name value="MechApe" />
      </metadata-restrictions>
    </authenticode-sign>
  </pe-file>
</artifact-configuration>
```

> Treat that as a sketch, not copy-paste. The schema is versioned and
> SignPath's artifact-configuration reference is authoritative — check it
> before saving. The editor validates as you type, and a wrong configuration
> fails at submission rather than shipping something unsigned.

## Configuring GitHub

**Settings → Secrets and variables → Actions**:

| Kind | Name | Value |
| --- | --- | --- |
| Secret | `SIGNPATH_API_TOKEN` | CI API token |
| Variable | `SIGNPATH_ORGANIZATION_ID` | organization GUID |
| Variable | `SIGNPATH_PROJECT_SLUG` | project slug |
| Variable | `SIGNPATH_SIGNING_POLICY_SLUG` | e.g. `release-signing` |

Only the token is secret; the rest are identifiers, and keeping them as
variables makes failed runs far easier to read.

## Cutting a release

```bash
npm version minor        # or patch/major — updates package.json and tags
git push --follow-tags
```

The tag triggers the workflow, which refuses to proceed if the tag and
`package.json` disagree, then runs lint and tests, fetches and
SHA256-verifies the llama.cpp runtime, builds, signs both passes, and opens
a **draft** release with the installer and a `SHA256SUMS.txt`.

**Each signing request needs manual approval in the SignPath web UI**, and
the workflow blocks waiting for it — that is why the job timeout is three
hours rather than the five minutes the build actually takes. Approve both
requests to let the run finish.

The release is left as a draft on purpose: install it on a real machine and
launch it once before publishing.

## Before approval comes through

The workflow does not fail without the secret. It detects that signing is
unconfigured, skips both passes, warns, and publishes an unsigned installer
whose release notes say so. Releases stay possible while the application is
pending — which matters, because a release has to exist before the
application can succeed at all.

## Verifying a signature

```powershell
Get-AuthenticodeSignature '.\MechApe Setup *.exe' | Format-List Status, SignerCertificate
```

`Status` must be `Valid`. The workflow already asserts this for `MechApe.exe`
after the first pass and fails the build if it is not, so a green run means a
real signature rather than a file that merely came back from SignPath.

A fresh certificate carries no SmartScreen reputation yet. Early downloads
may still warn; that fades as installs accumulate against a consistent
signing identity. Expected, not a misconfiguration.
